1. SPLIT THE ML PIPELINE INTO A PACKAGE  (item 1)
------------------------------------------------------------------------------
WHAT:
  The single 700-line file `src/components/ml_pipeline.py` was deleted and its
  logic moved into a new focused package: `src/ml/`.

  New files:
    src/ml/__init__.py        -> exposes `MLPipeline`
    src/ml/dtype_utils.py     -> normalize_dtypes() (bulletproofing, see #2)
    src/ml/problem_type.py    -> detect_problem_type() (classification/regression)
    src/ml/models.py          -> get_models() (the model registry per problem type)
    src/ml/preprocessing.py   -> build_splits() (feature plan -> encoded train/test)
    src/ml/training.py        -> train_and_evaluate() + metrics + best_model_name()
    src/ml/persistence.py     -> save_results() (models to GridFS, metrics to Mongo)
    src/ml/pipeline.py        -> MLPipeline orchestrator that ties it together

  The LLM agents were intentionally LEFT where they are (`src/agents/`), as you
  requested ("split file only, keep agents").

WHY:
  The old file mixed loading, preprocessing, model definitions, training,
  evaluation, SHAP, and saving in one class — and the train/evaluate logic was
  literally DUPLICATED (once in `train_and_evaluate`, once inline in `run`).
  Splitting it makes each concern testable and removes the duplication.

IMPACT / COMPATIBILITY:
  The only external user was `routes/ml.py`, updated to `from src.ml import
  MLPipeline`. The public interface is unchanged:
      MLPipeline(filename, target_column).run(progress_callback) -> dict
  The returned dict has the same keys the frontend already expects
  (problem_type, target_column, results, best_model, rank_metric, shap, ...).

2. BULLETPROOFED THE PIPELINE (no more dtype crashes)  (item 2)
------------------------------------------------------------------------------
THE BUG YOU HIT:
  "Cannot interpret '<StringDtype(storage='python', na_value=nan)>' as a data type"
  This happened because some CSVs load with pandas *extension* dtypes
  (StringDtype, nullable Int64/Float64, BooleanDtype). numpy/scikit-learn don't
  understand those, so `np.issubdtype(...)` in problem-type detection crashed the
  whole run.

THE FIX (you chose "no gate, just bulletproof it"):
  - src/ml/dtype_utils.normalize_dtypes(): on load, every extension dtype is
    downcast to a plain numpy dtype (nullable numbers -> float64, everything else
    -> object). Applied in MLPipeline.__init__ BEFORE anything touches the data.
  - src/ml/problem_type.detect_problem_type(): rewritten to use pandas type
    predicates (is_float_dtype, is_integer_dtype, ...) instead of np.issubdtype,
    so it can never crash on an exotic dtype.
  - src/ml/preprocessing._assign_roles(): keeps the earlier guard that reroutes a
    text column the LLM mislabelled as "numeric" (the 'Petrol' crash) to one-hot
    instead of sending it to StandardScaler.

  Net effect: a messy dataset is normalized and trained instead of crashing, and
  the pipeline returns real metrics. Verified end-to-end by forcing extension
  dtypes on a real dataset and running the full path with no error.

  NOTE: There is no "ML not available for this dataset" message anymore — per your
  choice we make the pipeline robust rather than blocking datasets.

3. FIXED AUTHENTICATION (couldn't bypass login before)  (item 3)
------------------------------------------------------------------------------
THE BUG:
  `App.jsx` had NO route protection. Anyone could open /upload or /dashboard/*
  by typing the URL. The only check was a weak `useEffect` that ran AFTER the
  page rendered.

THE FIX:
  - New file: frontend/src/components/ProtectedRoute.jsx
      * Reads the JWT from localStorage.
      * Decodes it and checks BOTH presence AND expiry (the `exp` claim).
      * If missing/expired -> clears the token and redirects to /login.
  - App.jsx wraps /upload and /dashboard/* in <ProtectedRoute>. Public routes
    (landing, login, signup) are untouched.
  - DashboardLayout.jsx: removed its now-redundant manual token check.

  The backend already enforced @require_auth on every API route, so this closes
  the frontend gap. Now the pages themselves are gated, not just the data.

5. FIXED "AI INSIGHTS NOT SHOWING" ON DATA INFO  (item 6)
------------------------------------------------------------------------------
ROOT CAUSE (this was subtle):
  The LLM was returning a VALID but LONG insights JSON. The shared call,
  `call_llm`, had a hard-coded `max_tokens=1024`. The richer insights JSON
  (summary + quality_flags + column_insights + correlations + recommended_target
  + feature_engineering + preprocessing + next_steps + uncertainty_notes) exceeded
  1024 tokens, so the reply was TRUNCATED mid-object, failed to parse, and the
  code fell back to empty insights -> nothing rendered.

THE FIX:
  - src/agents/llm_provider.call_llm now accepts a `max_tokens` parameter.
  - routes/analysis.py asks for max_tokens=3000 (env: GROQ_INSIGHTS_MAX_TOKENS)
    and a slightly longer timeout for the insights call.
  Verified: insights now come back fully populated (multi-sentence summary,
  several quality flags, 6 column insights, a recommended target, feature-
  engineering and preprocessing suggestions).

6. RESILIENCE ALREADY IN PLACE (carried over from earlier this session)
------------------------------------------------------------------------------

    the server's suggested wait.
  - Deterministic fallbacks so the pipeline never hard-fails on the LLM:
